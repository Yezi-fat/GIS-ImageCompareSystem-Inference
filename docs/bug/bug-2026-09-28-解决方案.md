## Function-Q1：SERVICE__DEFAULT_PROVIDER 修改后不生效

### 根因分析（三层叠加，按可能性排序）

**R1（最主要）：运行的是 CPU 镜像，GPU 路径根本不存在。**
`deploy/docker-compose.yml:19` 与 `deploy/docker-compose.prod.yml:20` 均使用 CPU 镜像
`gis-imagecomparesystem-inference-infer-service:latest`（不含 onnxruntime-gpu）；GPU 形态
（`Dockerfile.gpu` 构建的 `map-change-infer:gpu` + nvidia runtime）在 prod 模板中仅为注释示例
（prod yml 第 65~81 行）。CPU 镜像内 `capability.gpu_available()` 恒为 false，
`registry.get_engine()`（engines/registry.py:38-44）对 `local-gpu` 提示静默兜底 local-cpu。
**只改环境变量、不换镜像，配置永远不可能生效。**

**R2：取值形式错误时无校验、静默兜底。**
代码只识别小写连字符 `local-gpu`（registry.py:41 精确匹配）；若按 Java 枚举习惯写成
`local_gpu`（下划线），匹配失败 → 静默落到 local-cpu，启动与运行均无任何告警。
`config.py:37` 的 `default_provider` 为裸 str，无启动校验。

**R3（认知口径）：provider 判定权在 Java，Python 配置只是兜底。**
J-01 已闭环（Java侧待确认与待修改事项-回复.md A-1）：Java 正常路径**必带**
`X-Inference-Provider` 提示头（按 Java 自己的三级解析结果），仅远程熔断回放本地时才不带、
由 Python 默认配置兜底。因此端到端切换 GPU 的生效入口是 **Java 运行配置**
（`PUT /api/v1/config/inference`），Python 的 SERVICE__DEFAULT_PROVIDER 只覆盖兜底场景。
Java capabilities 的 `inference_provider` 聚合自 infer /health（实测 GPU 不可用 → LOCAL_CPU），
与前端"推理提供方：LOCAL_CPU"的显示一致；任务中 CPU 占用高 = 确实在 CPU 上跑。

**关于"是否有接口查询能力"：有，已存在。** `GET infer-service:8001/health` 返回
`gpu_available`（provider 列表存在）/ `gpu_usable`（试建会话通过）/ `vram_mb` / `models` /
`remote_configured`，即 Java capabilities 聚合的数据源（回复文档 A-4，Java DTO 已对齐）。

### 解决方案

**Python 侧（本仓库改动，小）：**

| 编号 | 改动 | 说明 |
| --- | --- | --- |
| Q1-P1 | `default_provider` 启动校验 | config.py 加 `field_validator`：合法值仅 `remote`/`local-gpu`/`local-cpu`，非法值（含 `local_gpu` 下划线形式）**启动即拒绝**并报出合法值清单——与 URL 启动校验（约束 #10）同一 fail-fast 纪律 |
| Q1-P2 | `X-Inference-Provider` 头校验 | 非法取值返 400 `INVALID_INPUT`（列出合法值），不再静默兜底 |
| Q1-P3 | 兜底告警日志 | `local-gpu` 提示因 `gpu_usable()=false` 兜底 local-cpu 时记 WARN（含 gpu_available/gpu_usable 实值），运维可直接从日志定位 R1 |
| Q1-P4 | 部署文档修订 | 《Python推理计算服务部署文档》补"provider 生效链路"一节：GPU 生效三要件（GPU 镜像 + nvidia-container-runtime + Java 侧配置切换），及 /health 自助核验方法 |

**运维操作（切换 GPU 的正确步骤，无需改代码）：**

1. 用 `Dockerfile.gpu` 构建 GPU 镜像（部署文档 §3.2），compose 换用 GPU 服务定义
   （prod yml 注释段已给出模板，含 `deploy.resources` GPU 预留）；
2. 确认宿主机 NVIDIA 驱动 + nvidia-container-toolkit 就绪；
3. `curl localhost:8001/health` 确认 `gpu_available=true, gpu_usable=true`；
4. Java 侧切换：`PUT /api/v1/config/inference`（管理员）将推理提供方改为 local_gpu（热生效），
   此后 Java 提示头带动 Python 走 GPU 会话；Python `.env` 的 `SERVICE__DEFAULT_PROVIDER=local-gpu`
   作为兜底保留即可；
5. 核验：推理时 `nvidia-smi` 有占用；响应 `actual_provider=local-gpu`；
   Java 任务详情 `provider=LOCAL_GPU, degraded=false`。

**Java 侧配合（建议，非必须）：** capabilities 可在 `inference_provider` 旁展示
infer /health 的 `gpu_usable`（配置值 vs 实际能力对照），降级任务前端可见 `degraded=true`
（字段已存在）。

## Function-Q2：地理要素与当前模型不匹配

### 事实核查（ONNX 元数据实读）

当前激活的分割模型 `landcover-yolo-v11/v1.0`（2026-09-23 交付）元数据实锤为
**EuroSAT 10 类检测模型**：`{0:AnnualCrop, 1:Forest, 2:HerbaceousVegetation, 3:Highway,
4:Industrial, 5:Pasture, 6:PermanentCrop, 7:Residential, 8:River, 9:Sealake}`。
业务目录为 4 类（森林/草地/雪山覆盖/建筑），确不匹配；且 **EuroSAT 无"雪"类**，
"雪山覆盖"在该模型下原则上不可支持。（另：仓库内 `yolo11/v1.0` 为 COCO 80 类通用模型，
元数据 names 同样完整——**类别表可从模型文件自描述读取，无需硬编码**。）

### 对用户提议方案的评估

用户提议："配置文件增加数组参数，模型输出 0…n 作索引取要素名称"。

**结论：方向对了一半，但不建议按原样采纳。**

- 合理的部分：**模型类别语义应随模型文件走、可被发现**——这点完全采纳（见 Q2-P1/Q2-P2，
  且 ONNX 元数据已自带 names，零成本）。
- 不建议的部分：**在 Python 配置里维护"索引→业务要素名"数组**。理由：
  ① 要素目录的单一事实源是 Java element_catalog（既定架构：类别扩展免前端发版，
  前端按 `/api/v1/elements` 动态渲染）；Python 侧再持一份映射 = 双写不一致源；
  ② 与既有契约重复——Java 每请求已下发 `class_mapping`（要素→模型类别），
  Python 配置数组会使"同一映射两处表达"；
  ③ 前端显示不匹配的修复点不在前端代码、也不在 Python 配置，而在**目录数据**：
  把 element_catalog 的条目与 `model_class_id` 改成当前模型实际类别即可，
  前端零改动。

### 解决方案

**Python 侧（本仓库改动）：**

| 编号 | 改动 | 说明 |
| --- | --- | --- |
| Q2-P1 | 新增 `GET /infer/models` 模型发现接口 | 扫描 `MODELS__DIR` 下 `{name}/{version}/`：返回 fp32/int8 产物齐全性、**类别表（读 ONNX 元数据 names）**、通道数、是否已加载、是否当前默认版本。只读、免鉴权豁免同 /health。（同时支撑 Q3） |
| Q2-P2 | `class_ids` 配置可选化 | 缺省时从模型 names 自动推导 `[0..C]`（C=背景通道，yolo_decode 末位背景约定）；配置与模型类别数不一致时启动/加载期明确报错（现有通道错配保护保留） |
| Q2-P3 | （可选）class_mapping 支持一对多 | 现契约要素→单个模型类别。若业务需要"草地=HerbaceousVegetation+Pasture"这类合并，schema 值扩展为 `int | list[int]`，蒙版提取改 `isin`。cv-common schema 变更，需 Java 同步——**建议仅在业务确认需要时做** |
| Q2-P4 | 过期注释清理 | config.py / local_onnx.py 中"class_mapping=COCO 序号+1、0=背景"的旧口径注释已废弃（现行：序号直用、末位背景），修正防误导 |

**Java 侧配合（必须的只有目录数据）：**

1. **目录重映射（立即见效，无需发版）**：element_catalog 的 `model_class_id` 按 EuroSAT
   类别表重映射（J-A2 既有结论；目录无写接口，走 SQL 或补管理接口）。例如：
   森林→1(Forest)、草地→2(HerbaceousVegetation)、建筑→7(Residential)；
   **"雪山覆盖"无对应类别，建议暂时下架（enabled=false）并向用户说明**。
   或按业务决策直接换成 EuroSAT 风格的 10 类目录。
2. 模型登记/激活页用 `GET /infer/models` 的类别表做映射校验与展示（防错配前置，
   现仅在推理时由 Python 兜底报错）。

**长期路线（根治）：** 用已交付的 `train/` 流水线自训 4 类业务模型
（0=forest 1=grassland 2=snow 3=building，含雪类），`export_onnx.py` 导出双产物落位后
Java 映射 forest→0…building→3。EuroSAT 模型仅作过渡。

**前端：无需改动**（目录驱动渲染）。

## Function-Q3：Java 模型列表不包含 models/ 中的模型

### 根因

Java 模型列表来自 Java 数据库的登记记录（`POST /api/v1/models`）；本部署的模型文件经
命名卷直接放置进 `models/`（内网交付形态，接口文档 §3.4 已认可"仅登记元数据"），
Java 无任何感知通道。

### 解决方案

**Python 侧：**

| 编号 | 改动 | 说明 |
| --- | --- | --- |
| Q3-P1 | `GET /infer/models`（与 Q2-P1 同一接口） | 即"推理服务实际可用模型清单"数据源：name/version/双产物齐全性/类别表/加载状态/是否默认。Java 模型管理页可调它展示与对账 |

**Java 侧配合：**

1. 模型管理页调用 `/infer/models` 展示"推理服务实际可用版本"，支持选中后一键登记
   （走既有 `POST /api/v1/models`，storage_key 按目录前缀约定填写）；
2. （可选）启动或定时对账：Java DB 登记记录 vs `/infer/models` 清单，不一致记 WARN。

**应急（零代码）：** 管理员按接口文档 §3.4 手工登记元数据
（`POST /api/v1/models`，storage_key 指向目录前缀），再 `PUT /api/v1/models/active` 激活。

## 咨询 Q1：配置项含义与注释

**方案（三层，单一事实源在代码）：**

1. **config.py 字段级 description（事实源）**：三服务 config.py 的全部 Field 补全
   `description="中文含义 + 生效方式"`（部分已有）；
2. **deploy/.env.example 行内注释（部署触点）**：逐项补注释——这是运维实际改配置的地方，
   当前仅部分有注释，补全之；
3. **docs/配置项说明.md（查阅入口）**：按服务列表格（环境变量 / 默认值 / 含义 / 生效时机
   [L1=重启生效] / 取值约束），由 scripts 从 pydantic Field description 半自动生成，
   防文档与代码漂移。

> 注：环境变量文件本身无法携带"类型化"注释，故注释层放在 .env.example 与说明文档；
> 代码 Field description 保证三者同源。
