## J-1【必改】element_catalog 按当前模型类别表重映射（Function-Q2）

**背景**：当前激活模型 `landcover-yolo-v11/v1.0` 为 EuroSAT 10 类检测模型
（ONNX 元数据实锤）：`0=AnnualCrop 1=Forest 2=HerbaceousVegetation 3=Highway
4=Industrial 5=Pasture 6=PermanentCrop 7=Residential 8=River 9=Sealake`；
Python 侧概率图通道 10 为背景（class_count=11，末位通道禁映射）。
现有 4 类业务目录（森林/草地/雪山覆盖/建筑）的 `model_class_id` 与之不匹配。

**改动内容**：更新要素目录数据（J-A2 既有结论；目录无写接口时走 SQL 或补管理接口）：

| 建议目录条目 | model_class_id | 备注 |
| --- | --- | --- |
| 森林 forest | 1 | EuroSAT Forest |
| 草地 grassland | 2 或 5 | HerbaceousVegetation / Pasture（取其一，业务定） |
| 建筑 building | 7 或 4 | Residential / Industrial（取其一，业务定） |
| 雪山覆盖 snow | — | **EuroSAT 无雪类，暂时下架（enabled=false）**；待自训模型（train/ 流水线，4 类含雪）上线后恢复 |

或直接换成 EuroSAT 风格 10 类目录（业务口径二选一，见解决方案"待确认项"）。

**约束**：
- `model_class_id` 取值范围 0~9（10 为背景，映射到 10 会在 Python 侧报通道错配/UNSUPPORTED 类错误）；
- 现契约 `class_mapping` 为**要素→单个模型类别**；若需"草地=HerbaceousVegetation+Pasture"
  一类多映射，须提前告知 Python 侧扩展 schema（解决方案 Q2-P3，当前未实现）；
- 前端无需配合（目录驱动渲染），改数据即生效。

## J-2【建议】对接模型发现接口 `GET /infer/models`（Function-Q3）

**背景**：Java 模型列表来自 DB 登记记录，对 Python 模型目录（命名卷直放）无感知。

**接口契约**（Python 侧已实现，V1.1 §1.4）：

```
GET http://infer-service:8001/infer/models
Header: X-Internal-Token（鉴权开启时必带；与 /infer/* 同口径，/health 豁免不含本接口）
```

响应（实测示例）：

```json
{
  "models_dir": "/models",
  "models": [
    {"name": "landcover-yolo-v11", "versions": [{
      "version": "v1.0", "fp32": true, "int8": true,
      "class_labels": ["AnnualCrop", "Forest", "HerbaceousVegetation", "Highway", "Industrial",
                       "Pasture", "PermanentCrop", "Residential", "River", "Sealake"],
      "class_count": 11, "loaded": false, "default_for": ["segmentation"]}]}
  ]
}
```

| 字段 | 说明与 Java 用途 |
| --- | --- |
| `fp32` / `int8` | 双产物齐全性——登记校验（fp32 缺失拒绝登记，int8 缺失告警，对齐 Java 接口文档 §3.4 既有约定） |
| `class_labels` | 类别名称表（索引=类别 ID）——模型管理页展示；element_catalog 映射核对的事实源 |
| `class_count` | 概率图通道数——`model_class_id < class_count-1`（检测模型末位为背景）范围校验 |
| `loaded` | 会话是否已加载常驻（运维诊断用） |
| `default_for` | 该版本当前承担的默认角色（`segmentation`/`change_detection`），与 Java"激活版本"对账 |

**建议对接方式**：
1. 模型管理页新增"推理服务实际可用模型"区块（调本接口展示）；
2. 登记/激活时用 `class_labels`/`class_count` 做映射校验（现仅推理时 Python 兜底报错，前置校验体验更好）；
3. （可选）启动或定时对账：Java DB 登记记录 vs 本接口清单，不一致记 WARN。

**注意**：Python v1.0.0 起 `class_ids` 可配置缺省（从 ONNX names 自动推导），
`/health` 与分析响应 `model_info.class_ids` 在模型未内嵌 names 时可能为 **null**——
Java DTO 请保持可空容忍（勿按非空断言）。

## J-3【建议】capabilities / 前端展示增强（Function-Q1 配套）

- 推理提供方展示建议区分**配置口径**与**实际口径**：`inference_provider` 为配置值，
  可在 capabilities 补充 infer `/health` 的 `gpu_usable`（实际能力），
  任务结果已有 `degraded` 字段（`actual_provider` 回映射，A-1 既有实现）；
- Python v1.0.0 起 GPU 兜底会记 WARN 日志 `gpu_unavailable_fallback_cpu`，运维监控可接入告警。

## J-4【确认项】provider 提示头取值校验收紧（行为变更，V1.1）

- Python v1.0.0 起，`X-Inference-Provider` 非法取值返回 **400 INVALID_INPUT**
  （原为静默兜底 local-cpu）。请确认 `InferenceRouter.toPythonProviderHint` 输出恒为
  小写连字符三值（`remote`/`local-gpu`/`local-cpu`，A-1 既有约定）——若已遵守则无影响；
- `SERVICE__DEFAULT_PROVIDER` 非法取值 Python 侧**启动即拒**（部署侧注意）；
- 端到端切换提供方的入口为 Java 运行配置（`PUT /api/v1/config/inference`），
  Python 兜底配置仅覆盖提示头缺省场景（详见部署文档 §9.1）。
