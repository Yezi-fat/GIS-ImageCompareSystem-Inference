## F-0 总结论：无需前端发版

本次变更的所有用户可见效果均经**数据**生效，前端按既有渲染逻辑自动跟随：

| 用户可见变化 | 生效机制 | 前端动作 |
| --- | --- | --- |
| 要素选择器与当前模型类别匹配（Function-Q2） | Java 更新 element_catalog 数据后，`GET /api/v1/elements` 返回值变化，前端动态渲染 | 无（自动生效） |
| "雪山覆盖"暂时下架（EuroSAT 模型无雪类） | 目录条目 `enabled=false` | 无（自动隐藏） |
| 自训模型上线后恢复 4 类业务要素（含雪） | 目录数据再次更新 | 无（自动生效） |

## F-1【建议】推理提供方展示口径说明（Function-Q1 配套）

**背景**：此前"推理提供方：LOCAL_CPU"的显示与实际执行可能存在口径混淆。
三层口径说明（供前端展示逻辑参考）：

| 口径 | 来源 | 含义 |
| --- | --- | --- |
| 配置口径 | `GET /api/v1/capabilities` 的 `inference_provider` | 系统当前配置的提供方 |
| 实际能力 | capabilities 可能新增 `gpu_usable`（Java 侧 J-3 增强，**未实现前勿引用**） | GPU 是否真实可用 |
| 实际执行 | 任务结果/详情的 `inference.provider` + `inference.degraded` | 该任务实际跑在哪个提供方、是否降级 |

**建议**：
1. 任务结果页如未展示 `degraded`，建议补充——`degraded=true` 时表示实际执行与配置
   不一致（如配置 GPU 但回退 CPU），可配 tooltip：「实际执行提供方与配置不一致，
   请联系运维核查 GPU 环境」；
2. 系统状态区展示 `inference_provider` 时，文案建议为"**配置**的推理提供方"，
   避免用户误解为"实际正在使用"。

## F-2【建议】要素目录异常态兜底（健壮性，非必须）

模型与目录错配时 Python 会返回明确错误（Java 透传后）：
`UNSUPPORTED_ELEMENT`（400，类别超出模型可识别范围）。
若前端当前对分析失败仅有通用提示，建议对该错误码单独文案：
「所选要素超出当前模型可识别范围，请联系管理员核对要素目录配置」。

## F-3 无需关注项（说明）

- `GET /infer/models`（模型发现）：Java 内部管理接口，前端不直接对接；
- provider 提示头取值校验、`class_ids` 自动推导：服务间契约，前端无感知；
- NLP 解析、差异分色、矢量化导出口径均无变化。
